# ARTEX worker integration (first slice)

Run the local scanner from an ARTEX worker's Bash tool:

```bash
cd /path/to/LLM-BugBounty-Automation
python -m integrations.artex_bridge https://authorized.example --scope config/my-scope.yaml --output /tmp/artex-scan-001
```

For an AI endpoint, add `--target-config config/targets/my-target.yaml --profile llm` to execute the testcase packs against that adapter. Without a target config, AI testcase packs report `skipped_no_target`; URL discovery alone cannot infer an arbitrary chat API's request schema. The scanner still applies the scope policy to adapter requests.

ARTEX supports user-defined script tools for workers. Generate a tool registration JSON with `python -m integrations.artex_tool_spec --scope /absolute/path/to/scope.yaml` and add `--target-config /absolute/path/to/target.yaml --profile llm` for AI packs. Submit this JSON to ARTEX's authenticated `POST /api/tools/custom` endpoint (or fill the custom-tool editor with the same fields). Paths must be visible inside the ARTEX server environment; when ARTEX runs in Docker, mount the repository, scope file, and Python environment into that container. Each invocation creates a unique output directory under `/tmp`, so concurrent workers do not reuse summaries. The script tool waits for the scan; ARTEX's command/Bash tool can switch long scans into a background job before JSON is returned.

The command prints one `artex-bridge/v1` JSON object. `assets` are original attack-surface items; `artex_assets` contains deduplicated, observed HTTP endpoints in ARTEX's `insert_assets` input shape. JavaScript paths with an unknown method remain only in `assets`. `findings` includes `graph_kind: finding` only for `confirmed` status; `candidate` and `unstable` statuses remain candidates for further worker investigation. Each finding includes a `report_path` for local evidence review. `pack_selection` records policy/budget decisions and `pack_executions` records whether selected tools actually ran; an empty finding list is not evidence that every pack ran. Tool summaries are omitted from this compact contract. A failed scan returns `ok: false` and exits nonzero, so a previous summary cannot be mistaken for a fresh result.

The ARTEX worker now ingests a successful `bugbounty_scan` response automatically. It calls the existing `insert_assets` path, checks its per-item receipt, records candidates and skipped test packs as facts, and stores only evidence-backed confirmed findings. A confirmed finding includes a sanitized evidence path and SHA-256 digest; ARTEX reopens the local file and verifies that digest before promotion. A report path alone does not prove a vulnerability. ARTEX serializes finding registration and uses a stable source key to avoid duplicate findings across concurrent workers. Each generated scan tool call uses a separate temporary result directory. The scanner's existing scope and policy gate still applies; a public URL requires an explicit scope file.

For the reverse path, generate both worker tools with `python -m integrations.artex_tool_spec --scope <scope.yaml> --include-verify` (add `--auth-contexts <accounts.yaml>` for named tester accounts). This prints an array; register each tool object separately with ARTEX. `bugbounty_verify` accepts candidate fields: `target_url`, `method`, `auth_context`, `prerequisites`, `success_criteria`, `observed_evidence`, and `vulnerability_type`, and returns `artex-verify/v1` JSON. The current executable type is `response_differential`, with `GET`, an empty `prerequisites` list, and `success_criteria: {"type":"body_contains","value":"<marker>","control_url":"<authorized control URL>"}`. It sends one control and two proof requests through the same scope, method policy, and request budget gates. Other types or prerequisite sequences return `unavailable` with a reason. Results are `confirmed`, `rejected`, `unstable`, or `unavailable`; ARTEX records non-confirmed outcomes as facts for planner follow-up and promotes only a confirmed result with verified local evidence to a finding. Executed verifications produce sanitized evidence and a local Markdown report under their unique result directory.

The integration exchanges JSON and invokes the MIT-licensed scanner as a separate process. ARTEX's graph and worker changes remain in the AGPL-3.0 repository; no Go or Python implementation is copied between repositories, and neither license or distribution layout is changed. A deployment that distributes modified ARTEX must continue to satisfy its AGPL-3.0 obligations.
